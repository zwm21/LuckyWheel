# LuckyWheel 重构规划 v2：核实记录与修订

日期：2026-09-20 ｜ 基线：`3b51038` ｜ 定位：本文是对 `docs/REFACTOR_PLAN.md`（下称 v1）的**逐项核实、修正与补充**，不重复 v1 已论证过的内容。v1 的结构方案与阶段划分继续有效，凡本文与 v1 冲突处以本文为准。

## 一、核实记录

v1 的核心论断我全部用独立手段复核了一遍，方法与被验证结论逐条对应如下。

仓库事实类，用 `git` 直接验证：65 个提交、5 个 tag（含一个误建的 `LuckyWheel`）、`.git` 目录 289MB、历史中 exe blob 合计约 289MB、`git ls-files` 实际只跟踪 4 个文件（`README.md`、`build_exe.bat`、`dist/LuckyWheel.exe`、`main.py`）。最后一条意味着 `.gitignore` 自身和 `wheel_data.json` 都不在版本控制内，v1 指出的"忽略了自己"属实。死代码用 ruff 0.16.3 扫过，比 v1 的说法多一项。

公平性偏差这一条值得特别说明单位问题。v1 表格里的 "+10.5%""+11.9%" 是**相对偏差**，不是百分点绝对偏差。我最初按百分点复现得到了 +2.6%，一度以为对不上，换算后确认一致：500k 次模拟下 n=4 最大扇区概率偏差为 +2.64 个百分点，折算相对偏差 +10.6%；n=10 为 +12.7%。机理也被精确复现——总转角区间实测 `[892.5°, 3142.5°]`，跨度 2250° 即 6.25 圈，落点密度在一个 90° 窗口内约为均值的 7/6.25 倍、其余区域 6/6.25 倍。任何不大于 90° 的扇区只要整体落进那个窗口就继承约 12% 的相对超额，所以扇区数与偏差大小几乎无关，这与 v1 的数值表吻合。**结论：v1 的公平性判断成立，不是偶发，固定起点路径下持续生效。**

最反直觉的一条也证实了。我用 `QT_QPA_PLATFORM=offscreen` 实际渲染了 n=4 的空文本转盘并逐点采样底色：item i 的文字绘制位置落在 `SECTOR_COLORS[n-1-i]` 的扇区上，而 `renderCache` 里判断文字用黑还是白时取的却是 `SECTOR_COLORS[i]`——底色取错成另一半圆。原因是 `QPainterPath.arcTo` 的正角度扫掠方向与文字定位用的 `(cos θ, sin θ)` 参数化方向相反，两者镜像。之所以用户从未发现，是因为 32 个调色板颜色的 lightness 实测范围是 91–229，没有一个 ≤ 50，对比色判断永远走黑色分支——一旦有人往调色板加一个深色，文字就会在错误的扇区上变白。这是全仓库最隐蔽的一颗定时炸弹。

`determineResult` 的角度公式经解析推导与模拟双重确认是正确的：扇区边界集合在镜像下自映射，`paintEvent` 的旋转与 `determineResult` 的反算共用同一套屏幕角度，所以指针下显示的文字和 `spinFinished` 报出的条目始终一致。v1 说"不要动它"，这一点我同意。`rot=0`、n=4 时指针恰好压在扇区边界上，属于平局而非错误。

其余核实项：26 个 `saveData()` 调用点、数据集 41 项中 17 个唯一文本（重复率 42%，字号求解缓存的理论命中率约 58%）、`.gitignore` 第三、四行使打包必需的字体在新克隆上必然缺失——均与 v1 描述一致。

## 二、对 v1 的修正

**M1 死代码清单不全。** v1 列了 4 个未使用导入，ruff 实测为 5 个，漏掉 `QFileDialog`（main.py:17）。另有一处 v1 未提的死赋值：main.py:715 `item_text = selected.text()` 之后两行即被 `item_text = group['drawn_items'][current_row]` 覆盖，第一次赋值从未被读取。

**M2 高性能帧率依赖，v1 完全未覆盖。** `updateRotation` 按固定 `timer_interval = 30`ms 推进，`friction = 0.98` 是**每帧**衰减而非每秒衰减。系统负载高、定时器迟到时，动画视觉上变慢但物理模型照常计数，快慢两台机器上手感不同；若将来有人把间隔改成 16ms，同一初速度的总转角将差一倍。正确做法是用真实经过时间（单调时钟）算 `dt`，衰减改为按时间的指数模型 `v *= exp(-k·dt)`，帧率无关。

**M3 `secrets` 用于初速度是过度工程。** main.py:271 用密码学随机数生成旋转初速度，每次抽奖多一次无意义的安全随机调用。`random` 模块在此语义正确且更快。同理 `random.shuffle(SECTOR_COLORS)` 在模块导入后原地打乱一个被十二处引用的全局常量，应改为生成副本或换成确定性取色。

**M4 `setItems` 重置 `rotation = 0` 是把公平性问题和视觉跳变问题焊在一起的根源。** 批量抽取每一轮、单次抽取后每次按「抽出」都经过 `updateWheelFromCurrentGroup` → `setItems`，起始角一律归零，于是"6.25 圈"偏差在常见路径上持续生效；同时用户每次操作都看到转盘啪地跳回 12 点。v1 在 1.2(A) 提到了前半句，但没有把它作为独立缺陷列出。重构时 `setItems` 不应清零旋转角，起始角应当跨次累积，这是成本最低的一半修复。

**M5 统计检验必须写死单位和基线。** 阶段 3 的 `test_fairness.py` 若只写"最大偏差 < 1.5%"会埋坑：相对偏差和百分点偏差差 12.5 倍（n=8）。测试应断言相对偏差，并以本轮实测的当前基线（n=4 约 +10.6%、n=8 约 +11~13%、n=10 约 +12.7%）作为对照，重构后目标压到 1.5% 相对偏差以内。

**M6 测试不能依赖被忽略的真实数据文件。** `wheel_data.json` 在 `.gitignore` 里且属于用户运行时数据。v1 的 `tests/data/` 方向正确，但要显式划定：当前工作区那份 41 项的数据只作为本次调研样本，**不得**成为 fixture；fixture 复制其形状（含大量重复项）后独立维护。

**M7 v1 忽略了入口兼容。** README 与用户习惯都是 `python main.py`，v1 目标结构是 `src/` 布局加 `python -m luckywheel`。保留一个三行的 `main.py` shim 转调 `luckywheel.app:main`，成本为零，避免打断肌肉记忆和老版 `build_exe.bat` 之外的一切外部引用。

**M8 一个可选优化，价值不高，列出备查。** SECTOR_COLORS 按 `i % 32` 顺序取色，项目数 ≤32 时无重复、够用；但项目数恰为 24 之类时，首尾两色会在转盘上正好相邻对比。可在 `core/layout.py` 里改为按黄金比例或均布间隔从调色板取色，纯属观感项，不要排在必修项之前。

## 三、对 Plan 的补充

**P1 特征测试应包含"文字落在哪个扇区"的像素级快照。** 阶段 0 钉住现状时，除 v1 列的三条外，加一条离屏渲染后采样每个文字坐标处底色与 `SECTOR_COLORS` 下标的对应关系。这条测试在阶段 3 修配色时应当由绿翻红——它是全仓库唯一能自动捕获"顺手把镜像改对了"的东西，防止有人在不知道 `arcTo` 方向的情况下"修好"一半留下另一半。

**P2 端到端公平性，而非只测 `plan_spin`。** 阶段 3 除 core 层卡方外，GUI 侧应断言"动画结束 emit 的 winner 与指针实际指向的文字一致"，这正是当前 `onSpinFinished` 弃用 `index` 参数埋下的坑：信号契约在 Widget 侧要真正被消费，端到端测试才能防回归。也顺带把"emit 的 index 与 `items[index]` 一致"写成不变量——它与配色反转无关，按索引抽出的修复成立。

**P3 按索引抽出的修复还要处理重复项在数据模型里的歧义。** v1 正确地指出了 `items.remove(text)` 删第一个匹配的问题，修复方向是 `pop(index)`。但可以更进一步：给 `core/models.py` 的条目引入稳定 id（如 `Entry(id, text)` 序列化为 `{id, text}` 或退化回纯字符串列表）。纯文本列表下重复项无法区分外观，用户问"我抽的是哪个 1"时无解。这是数据模型升级，建议放进阶段 2 随 schema v2 一起做，迁移函数把旧纯字符串升级为带 id 的条目，向后兼容读取。

**P4 保存调度器要覆盖的两个隐藏热点。** v1 提到字号 spinbox 每次 `valueChanged` 全量落盘。实际测过调用点后还有两个：`SplitterHandle.mouseReleaseEvent` 的保存（次要），以及批量抽取每一轮的 `saveData`。去抖统一到 500ms 合并窗口即可，`closeEvent` 强制 flush。另外原子写用 `os.replace` 时要处理目标目录不可写（Program Files 场景）的回退，v1 的 `paths.py` 已经覆盖，两处要联动。

**P5 QSS 约束的回归测试要覆盖具体颜色而不仅是"不崩"。** v1 提到"不要给带滚动条控件单独设 QSS"这条坑（对应 commit `b34d41d`）。测试不能只断言渲染不抛异常——`QStyleSheetStyle` 的劣化在 offscreen 下未必可见。可行的断言是：`initUI` 之后 `list_widget.styleSheet()` 与 `drawn_list_widget.styleSheet()` 均为空字符串，以及每个显式设过 QSS 的 frame/label 的白名单。这是白名单式约束，将来有人手痒给列表加圆角就会红。

**P6 Release 链路要在重写历史前跑通，且 tag 策略要改。** v1 的阶段 1 次序（先 Release、后历史重写）正确，补充一条：exe 退出版本控制后，tag 是唯一的版本锚点，当前 5 个 tag 中有 4 个指向含 exe 的提交，重写后这些 tag 会指向新 hash。Release 上传用 `gh release upload <tag>` 补挂旧 exe 时，要确认 GitHub Release 与 tag 的关联是否随 force-push 失效——这一步应在沙箱 fork 上预演一次，不要直接对 `origin` 操作。

**P7 预提交钩子里二进制拦截的具体形态。** v1 提到本地 hook 拒绝 `dist/` 下的暂存文件。补一个更强也更不容易绕过的形式：`.gitattributes` 把dist/`*.exe` 标记为 `binary`，pre-commit 用 `git diff --cached --name-only | grep '^dist/'` 直接拒。同时 CI 里加一条 `git ls-files | grep -E '\.(exe|ttf)$'` 必须为空的守卫，防止有人从别的路径（如 `assets/`）把字体误提交回来。

## 四、修订后的执行顺序

骨架仍按 v1 的六阶段，各阶段的交付物以 v1 为准，本节只列差异。

阶段 0（安全网）先做，测试清单在 v1 三条特征测试上加 P1 的像素快照、P5 的白名单约束和 M5 的公平性基线记录。这一阶段结束时应能回答"当前偏差到底是多少"并留证。

阶段 1（卫生与历史重写）风险最高、时效性最强，放在安全网之后立即执行，这是 v1 的判断，我同意：越晚做，重构期间的提交越会被一并改写。本阶段补 P7 的双重拦截（hook + CI）和 M7 的 `main.py` shim。

阶段 2（抽离 core）只搬不改的那条纪律不变，唯一例外是存储的原子写、损坏保留和 schema 版本必须同步落地，理由 v1 已说透。本阶段把 M2、M3 的物理与随机源修正一并做掉——它们只在 core 内部，不涉及 UI，且 M2 会让阶段 3 的动画改造站在正确的时间基础上。

阶段 3（算法修正）是净收益最大的一步。公平性改为先定结果再播动画（v1 决策保留）；按索引抽出；字号二分加唯一文本缓存（这批数据上有 42% 重复，命中率可观）；缓存失效守卫与 HiDPI；P3 的条目 id 随 schema v2 一起。配色反转也在此阶段修正，修正时以 P1 的像素快照翻红为信号，改完更新快照并在 CHANGELOG 记录"文字对比色此前取错底色，因调色板全为亮色而未暴露"。

阶段 4（UI 分层）拆面板、删 `SplitterHandle` 用垂直 `QSplitter`，这条 v1 已充分论证，无需补充；只强调一点：`resizeEvent` 里那段失效的钳制逻辑（`max(800, ...)`）删除后，列表高度行为完全交给 `QSplitter`，这是行为变化，需要一条 GUI 回归测试覆盖"窗口缩到最小尺寸时两个列表仍可操作"。

阶段 5（收尾）README 按新结构重写时补上公平性说明的措辞要克制：程序先等概率选中再把动画演到对应位置，观感不变，不是"内定"的暗箱。

## 五、风险登记

v1 的两条主要风险（历史重写不可逆、阶段 3 手感可能变化）继续有效。本次核实新增三条。其一，公平性修正会改变每一轮的实际结果，若用户手里存有依赖旧偏差的"手感预期"不会有任何数据影响，但批量抽取的历史结果分布会与之前不完全可比——不算风险，记录备查。其二，条目 id 的引入使磁盘格式变化，旧 `wheel_data.json` 必须能被无损迁移，迁移失败时要保留原件而非重置，这与阶段 2 的原子写是同一条防线，两边测试要互相引用 fixture。其三，`python -m luckywheel` 的 src 布局在 PyInstaller 下的入口解析与普通运行不同，打包脚本要在阶段 1 就改并验证一次，不要留到收尾才发现 `--onefile` 找不到模块。

如果这份规划获得认可，第一步不是写代码，而是阶段 0 的两件事：`git clone --mirror` 备份到工作区外，以及把 v1.0.1~v1.0.4 的四个 exe 从 GitHub Release 下载归档。这两步做完之前，任何对历史和构建链路的改动都不该开始。这两步需要访问 GitHub 的网络操作，执行前我会先确认再动。
